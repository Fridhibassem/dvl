# 1. NON-NEGOTIABLE DVL UNDERSTANDING PIPELINE

The DVL understanding path is **not adaptive** for this re-test.

Every project passes through the ordered four-stage understanding
pipeline:

``` text
USER INPUT / REPO / PROJECT SOURCES
        ↓
SOURCE INTENT BASELINE
        ↓
P/N — NORMAL PLAN + NORMAL GRAPH
        ↓
P/S — SMART PLAN + SMART GRAPH
        ↓
P/UL — ULTRA PLAN + ULTRA GRAPH
        ↓
P/ULTPR — ULTRA-PRO RE-AUDIT / DEEP GRAPH
        ↓
CANONICAL URG — ULTRA RELATION GRAPH
```

The stages may be cheap or expensive depending on project size, but
**the stages are not optional**.

Do not replace this with:

``` text
Normal → Smart → maybe Ultra → maybe Ultra-Pro
```

and do not call it "adaptive understanding" or "adaptive depth".

### Why the four stages exist

The purpose is not ceremony. It is progressive understanding while
preserving the product the user actually asked for.

``` text
P/N     = capture explicit accepted intent
P/S     = structure what is directly implied
P/UL    = recursively discover hidden execution-relevant relations
P/ULTPR = attack the Ultra result itself for missed relations/assumptions/failure cases
```

Golden law:

> **Depth may increase. Intent may not drift.**

Lineage must remain traceable:

``` text
SOURCE INTENT
   ↓
NORMAL
   ↓
SMART
   ↓
ULTRA
   ↓
ULTRA-PRO
   ↓
URG RELATION
   ↓
TASK CONTRACT
   ↓
OUTPUT + EVIDENCE
```

A deeper pass may discover missing work, dependencies, resources,
invariants, consumers, gates or evidence requirements. It may not
silently redefine the accepted product.

# 4. NORMAL → SMART → ULTRA → ULTRA-PRO

## 4.1 P/N --- Normal

Normal captures the accepted explicit request: goal, actors/users,
explicit features, constraints, accepted decisions and acceptance
expectations. It should avoid unnecessary invention.

## 4.2 P/S --- Smart

Smart adds directly implied structure: stable entities/IDs, direct
dependencies, inputs/outputs, consumers, interfaces/contracts, direct
invariants, missing explicit questions, acceptance structure and
provenance.

Question:

> **What is directly implied by what the user requested?**

## 4.3 P/UL --- Ultra

Ultra recursively searches hidden but execution-relevant relations:

``` text
Trigger
  ↓
Effect
  ↓
Hidden consequence
  ↓
Relation / invariant / missing work / resource consequence
  ↓
Treat the finding or fix as a new trigger
  ↓
Search again
```

It searches data flow, control flow, state transitions, resources,
concurrency, failure/recovery, integration, consumers, external effects
and verification/invalidation consequences.

## 4.4 P/ULTPR --- Ultra-Pro

Ultra-Pro attacks the Ultra result:

-   What relation did Ultra miss?
-   What assumption is being treated as fact?
-   What changes under concurrency?
-   What happens after crash/retry/recovery?
-   What if an external system is delayed or contradictory?
-   What if a resource disappears?
-   Can the invariant actually be enforced?
-   Does the proposed fix create another consequence?
-   Is an actor, timer, consumer, gate, transition, resource, task or
    evidence requirement missing?

Ultra-Pro is a re-audit/deepening mechanism, not permission to rewrite
intent.

# 5. URG --- ONE CANONICAL RELATION GRAPH

URG is the canonical machine graph of all **currently discovered**
execution-relevant project relations. "Currently discovered" does not
mean omniscient.

Visual graphs are projections. Task Contracts are execution projections.
Neither becomes a second canonical relation truth.

Relations may express dependencies, producers/consumers, resource
use/conflicts, serialization/parallel safety, gates, verification,
invalidation, external effects and provenance.

Runtime discoveries are proposals until DVL validates them. A
Worker/Provider statement alone does not rewrite URG truth.

# 6. DETERMINISTIC GRAPH-TO-TASK COMPILER

The Compiler does not reason like another AI brain. It projects the
accepted URG into execution-ready Task Contracts.

Required properties:

-   preserve stable Task identity where meaning is unchanged;
-   preserve relation lineage;
-   no silent relation loss;
-   no silent invention/rename/merge/delete of canonical meaning;
-   explicit dependencies, inputs, outputs and consumers;
-   explicit resources/conflicts;
-   explicit evidence requirements;
-   explicit risk/control requirements when already established by DVL
    state;
-   dynamic execution state may be GO / WAIT / HOLD / ASK_USER / BLOCK;
-   compiler output grants **no authority**.

Task Contracts are projections. Assignment + Kernel own authority.

# 7. SMART ORCHESTRATOR + SMART DÉCALAGE

Optimization target:

> **Maximum safe useful concurrency --- not maximum worker count.**

Smart Décalage law:

> **Delay by state, not by arbitrary timer.**

State can include prerequisite readiness, resource conflicts,
verification pressure, human/external gates, recovery, unresolved risk
and Provider/context/quota danger.

The graph describes relations. Orchestrator/Décalage schedule.
Kernel/runtime enforce boundaries.

An 8 GB Mac must not interpret hundreds of logical Tasks as hundreds of
physical Workers. Logical workload and physical concurrency are
different quantities.

``` text
Task = durable work identity
```

> **Task → Assignment → Worker**

# 9. KERNEL + HARNESS

Kernel is law, not planner/reviewer/orchestrator.

It owns/enforces identity, Assignment authority, scope, stale-authority
fencing, isolation, allowed/forbidden actions, durable control truth,
security policy, execution constraints, evidence authority and
integration prerequisites.

Harness executes what Kernel allows and owns execution mechanics:
provider adapter, context preparation, tool loop,
filesystem/terminal/tests/browser/DB/MCP, process supervision,
sandbox/container where supported, usage/budget observation, checkpoint
creation and safe stop support.

Restricted-role law remains:

> **No real sandbox → no shell for restricted roles.**

# 10. PROVIDER TOKEN / CONTEXT / QUOTA / SAFE HANDOFF

This is not an optional side feature. It is part of safe execution
because:

> **Provider budget can die. Project work must survive.**

Signals are always truthful:


Never invent remaining tokens/context/quota.

Preserved state machine:

``` text
GREEN
  ↓

  ↓

  ↓
SAFE BOUNDARY
  ↓
CHECKPOINT + EVIDENCE + STATE FLUSH
  ↓
FENCE / REVOKE / HIBERNATE / STOP
  ↓
CONTEXT REBUILD
  ↓
```

When capacity is UNKNOWN, prediction cannot be trusted. Bounded

Safe Handoff must reuse recovery/fencing primitives rather than creating

A replacement Worker receives reconstructed project/task state; it does
not inherit the previous Worker's authority merely because it inherits a
checkpoint.

# 11. REVIEW / SECURITY / RISK --- MOUNTED ON THE EXISTING TASK SYSTEM

Review/Security/Audit do not create a second brain.

Risk vocabulary:

``` text
Family    = where the task belongs / risk context
Indicator = whether this task/output carries risk
Level     = LOW / MEDIUM / HIGH / CRITICAL (exact final policy remains testable)
Control   = required review/security/verification/audit action
Consumers = blast radius / downstream impact
```

Principle:

> **Family gives context. Indicator gives control. Consumers give
> impact. Kernel enforces stop.**

Risk depends on
product/environment/users/data/traffic/exposure/operational
criticality/output/consumers, not only the changed code.

For a risky producer:

``` text
Implementation complete
        ↓
Required Review/Security controls
        ↓
Verification
        ↓
PASS
        ↓
Affected consumers may proceed
```

Unrelated Tasks continue. This preserves Smart Décalage and avoids
global choking.

Review/Security are generated bounded control Tasks. They receive the
relevant task contract, output/candidate, dependencies, consumers,
invariants, risk context and evidence. They may produce
findings/evidence; they may not silently change Project Truth.

An LLM review alone cannot issue authoritative Verification PASS.

# 12. EVIDENCE → VERIFICATION → INTEGRATION

Evidence may include diffs/snapshots, command/test/build/migration
results, screenshots/browser results, runtime observations, security
scans, generated artifacts and scoped human acceptance.

Law:

> **Activity shows motion. Evidence proves outcome.**

Verification judges the candidate/evidence against acceptance criteria,
invariants, guards, required controls and expected result.

Integration then revalidates the exact candidate against **current**
project truth. A previous PASS may be stale after relevant project
decisions, policy, risk, environment, dependency or merged-candidate
changes.

Only Integration changes official Project Truth.

# 13. MODULE AUDIT + RELEASE/FULL-PRODUCT AUDIT

Audit is broader than per-task Review/Security.

``` text
Task controls
    ↓
Integration
    ↓
Module Audit
    ↓
Integrated product / release candidate
    ↓
Release / Full-product Audit
```

Audit examines composed behavior and cross-module seams that task-local
controls can miss.

Audit produces evidence-backed findings, not silent fixes.

``` text
Audit finding
    ↓
Fix Task
    ↓
normal DVL pipeline
    ↓
Review/Security if required
    ↓
Verification
    ↓
Integration
    ↓
Affected audit re-evaluation
```

An unresolved local finding blocks only its affected gate unless it is
genuinely a shared release prerequisite.

# 17. CANDIDATE CORRECTIONS TO MOUNT FOR THE NEXT RE-TEST

These are **not frozen law**. They are the smallest consolidated
candidate refinements supported by one or both simulations. Claude must
attack them, not merely accept them.

### CAND-A --- Authoritative admission/fencing boundary

Assignment/resource/account admission must be a conditional
authoritative commit against current revision/epoch/scope. A stale
Assignment must not mutate authoritative state. In-flight action
semantics at revoke must be explicit; if an already-running process
cannot be safely stopped, keep its workspace isolated and prevent any
Project Truth route.

### CAND-B --- Committed checkpoint + replay identity

Checkpoint publication needs a durable commit identity/manifest/hash or
equivalent integrity boundary. Partial checkpoint ≠ committed
checkpoint. Replay must reconstruct authority/state without reviving
stale actors.

### CAND-C --- Candidate/evidence freshness binding

Verification evidence must bind the exact candidate and relevant current
assumptions: base/project revision, relevant decisions,
policy/risk/control set and environment where material. Integration
atomically rechecks freshness. The exact schema/name is not frozen here.

### CAND-D --- Batch/seam revalidation

Individual PASS results cannot simply be concatenated into a combined
PASS. Material merged output must be rechecked at affected
semantic/security seams before Integration.

### CAND-E --- Token/context continuation fit

Safe Handoff remains GREEN→AMBER→RED→safe
boundary→checkpoint→fence→resume/reassign. The continuation package must
fit the target Provider/context. If no permitted target can continue the
remaining work, DVL must not loop forever; it needs a scoped
split/recompile/replan path preserving lineage. Claude proposed
`≤ 0.35 × target window`; **that number is experimental and is not
frozen**.

### CAND-F --- Capacity truth + hysteresis

Capacity signals remain REPORTED / ESTIMATED / UNKNOWN. Stale-epoch
usage may be useful as observation but never authority. Real provider
exhaustion/errors must not be erased by a stale projection. Admission
transitions need enough hysteresis/latching to avoid oscillation. Exact
thresholds are experimental.

### CAND-G --- Physical host admission by resource profile

Physical concurrency must be admitted against RAM/CPU/process/tool
profiles and headroom, not only Worker count. Host-caused death must not
automatically be classified as Provider failure. Exact resource numbers
must come from the real 8 GB Mac.

### CAND-H --- External effect identity + ambiguity

Irreversible/non-idempotent effects require durable logical identity
tied to durable project work and declared effect meaning, plus
provider-specific reconciliation/idempotency where available. If outcome
remains ambiguous, HOLD/ASK in the affected scope; never blind resend.
Effects that bypass DVL mediation remain an open containment problem.

### CAND-I --- Review independence as evidence quality

Where separate providers/models are available and required, use them. If
unavailable, do not fabricate independence. Single-provider operation
remains possible but must expose degraded separation honestly. Exact
mandatory diversity policy remains to be tested by risk level.

### CAND-J --- Audit convergence

Audit findings require stable identity/lineage and evidence. Repeated
unchanged/unreproduced findings must not create infinite fix loops. But
removing noisy loops must not remove intentional coverage. Required
audit passes/coverage must be explicit and risk-based; Claude's exact
"two passes" is a candidate, not frozen law.

### CAND-K --- Consequential acceptance oracles

Consequential Project Decisions should have executable or independently
checkable acceptance criteria where feasible. Oracles are evidence
mechanisms, not a new brain and not permission to redefine user intent.

### CAND-L --- Relation lifecycle

Runtime-discovered relations need provenance/status so
inferred/proposed/rejected/accepted relations are not confused. Only
accepted execution-relevant relations may authoritatively alter Task
contracts/gates.
